## Original photos, export and backup (R3-04, R3-11, #135 D1)
- **REQ-OR-01** For every photo saved from now on, Robia keeps an "original": exactly the frame the cutout engine processed (EXIF orientation applied, same pixels the engine saw, before background removal and before the crop), saved as JPEG quality 90. Its size therefore equals the Robia photo's working size, never more: long edge 1024 px for the precise engine, ≤ 2048 px (power-of-two decode, e.g. 4000 → 2000) for Standard; ~0.15–0.7 MB. This answers Manu's "2048 me parece mucho": the original is never larger than the frame Robia already works on, and reprocessing it reproduces the same result. Stored next to the cutout in app storage; referenced from the garment row. Existing garments have no original (UI hides original-only actions for them).
- **REQ-OR-02** With each original, Robia stores the processing recipe needed to reproduce the cutout from it: engine (ML Kit / precise), the cutout options in force, the work size, the applied rotation, and the crop rectangle in original-pixel coordinates. "Reprocess from original" (editor Redo for saved garments) reproduces the stored cutout within a tolerance of IoU ≥ 0.98 of alpha > 0.5 when run with the same recipe (JVM test on a fixture; device check).
- **REQ-OR-03** The raw camera/gallery copy and the intermediate `subject-*.png` are deleted after a successful save (today they are orphaned forever); a one-time cleanup removes existing unreferenced `gallery-*`, `camera-*` and `subject-*` files older than 24 h that no garment or open draft references.
- **REQ-OR-04** Originals are backed up to Google Drive **[Q 1 = A]** under `originals/<garmentId>/<hash16>.jpg`, referenced by optional fields in the snapshot photo record (`originalBlobPath`, `originalHash`, `originalByteSize`, `recipe`); snapshot `schemaVersion` stays 2 so older app versions keep working; restore downloads originals after cutouts and a missing/failed original never blocks or guards the garment restore; purge, integrity check and Drive usage count originals separately ("Originals" line in Drive usage). Old app versions that re-upload a snapshot without these fields must not cause deletion of `originals/` blobs (purge only by the new app, only for garments whose snapshot record is gone).
- **REQ-OR-05 (#135 D1)** In the photo editor, Keep mode can paint back the removed background for garments that have an original, by mapping the original into the cutout's coordinate space with the stored recipe. Garments without an original keep today's behaviour (documented limitation).
- **REQ-EX-01 (R3-04)** The share button in item detail opens an "Export" screen: Photo = Robia photo | Original photo (the latter only when an original exists); Format = Image | PDF; Show = switches for Name, Category, Colours, Occasions, Seasons, Fit, Location, Notes (defaults: Name, Category, Colours, Occasions on). Choices persist across exports. Preview button shows the result; Share opens the system share sheet.
- **REQ-EX-02** Image export renders a vertical card (photo on the backdrop, then the chosen fields as text/chips, small "Robia" mark), PNG, long edge 1600 px. PDF export reuses the current A4 design with only the chosen fields. Empty fields are omitted, never shown as blank rows.
- **REQ-ZIP-01 (R3-11)** Settings › Google Drive gets "Download all my data (.zip)". It builds the archive from the phone's local data (works offline), asks where to save with the system file picker, streams (no full in-memory copy), and shows progress with Cancel. Contents: `robia-data.json` (the same JSON as the Drive snapshot), `photos/` (cutouts), `originals/` (when present), `README.txt` (format, date, app version). Excludes models, caches and thumbnails. No import in this round.

## Duplicate detector (R3-07)
- **REQ-DU-01** Two tiers: **Same photo** = identical image `input_hash` (no threshold); **Very similar** = IMAGE cosine ≥ T_dup AND same category AND (if both have a primary colour) same primary colour. T_dup is a constant chosen by the calibration gate G-DUP (below); until then only "Same photo" is active. Archived garments and garments without a current IMAGE vector are excluded; a garment whose stored vector's `input_hash` does not match its current photo is re-embedded before it can be paired.
- **REQ-DU-02** Groups = connected components of qualifying pairs, max 6 garments per group (larger components split by strongest pairs). Pairs dismissed by the user are never shown again **[Q 6 = A]**: persisted in Room and carried in the Drive snapshot as an optional list, so they survive a reinstall/restore.
- **REQ-DU-03** Browse shows a banner "Possible duplicates found · N groups to review · Review" in the same slot as the suggestions banner, only when undismissed groups exist; not shown while a review/restore/sync prompt is visible. The review screen lists groups; each garment has Keep/Delete (default Keep); per group "Not duplicates"; bottom button "Delete N garments" with confirmation (destructive colour). Delete = existing archive path.
- **REQ-DU-04** The scan runs on a one-shot snapshot (not the observed flow), off the main thread, after the embedding backfill settles and at most once per day or after N=5 new garments; ≤ 500 garments in ≤ 2 s on the Poco F3.
- **G-DUP (gate)** Developer-mode "Duplicate calibration" lists the top 30 most similar same-category pairs with their cosine; Manu marks each Same/Different; the coordinator sets T_dup = the lowest cosine that keeps precision 100 % on his marks (plus 0.005 margin) in a PLAN-CHANGE. Evidence from planning (`artifacts/inv-r3-models.md` §Duplicates): on 142 photos with background, different black dresses reach cosine 0.955–0.977 while re-shots of the same garment reach 0.966–0.989, so cosine alone cannot be trusted below ~0.98 without the category/colour conditions.

## Cutout quality (N3, N5, #135 D2/D3)
Evidence (`artifacts/inv-r3-cutout.md`): the Python reference pipeline (`tools/segmentation-bench/pipeline_v11.py`, chosen variant) keeps Manu's pink shorts complete and removes the wooden bar; the app removed the interior and kept the hanger. MediaPipe 1.1.1 in Python (same version and model as the app) returns the same selection masks as the raw model. So the defect is in the Android path (wiring, a stage divergence or a silent fallback), not in the algorithm; the precise engine was never device-tested on raw photos (G-SEG-1 used already-processed PNGs).
- **REQ-CU-01 Diagnostics (developer, debug build).** A debug-only launch extra runs both engines on every image placed in the app's external files dir `cutout-debug/in/` and writes, per image, every stage of the precise pipeline (S1 saliency, each S2 selection and the union, S3 boxes with scores, S4 kill mask, S4b filled photo + reselection + band, S5 alpha, final cutout) as PNG plus `report.json` (sizes, timings, engine, fallback reason), and the ML Kit result. Every normal cutout logs one line `cutout_result engine=<precise|mlkit> fallback=<none|timeout|error|not_removed|tripped> ms=<n>`. The same stage names are produced by a Python script from the reference pipeline so the coordinator can compare stage by stage (IoU per stage).
- **REQ-CU-02 Precise engine fixes.** From the diagnostic evidence plus this closed list: (a) the band reselection never removes more than 15 % of the garment area the first selection had inside the band (otherwise keep the first selection there); (b) a final garment-loss guard: if the final opaque area is < 70 % of the S2 selection area, the precise result is rejected and Standard is used, logged as `fallback=garment_loss`; (c) SAM inputs are scaled exactly as the reference (long edge 1024, points scaled) for photos whose work size is not 1024; (d) any wiring defect found by the diagnostics. Acceptance: on the diagnostic set (Manu's pink and red shorts + 8 photos from the precision set), every stage mask has IoU ≥ 0.95 with the reference and the final alpha IoU ≥ 0.97.
- **REQ-CU-03 Hanger-band edges (N5).** Edges in the hanger band are as crisp as elsewhere: inside the band the edge filter uses the filled photo as its guide and the edge profile of the rest of the garment, and pixels within 2 px of the removed hanger take the fill colour before compositing (no hanger-coloured fringe). Measured on the red shorts: mean alpha transition width in the band ≤ 1.5× the width on the sides (script in the diagnostics tool).
- **G-CUT (gate, Manu, device)** After K02+K03: Manu redoes ≥ 10 garments (pink and red shorts, ≥ 3 on hangers, ≥ 2 white-on-white) with Experimental (precise) and Standard and rates each OK/NOK. Pass = precise NOK < Standard NOK and no garment part lost that Standard kept → Manu decides whether the default returns to Automatic. Fail → precise stays Experimental and off; the next step is decided with Manu.

## Photo editor (N4, answer 8)
- **REQ-ED-01 Smart selection works and is visible.** In Remove and Keep modes the smart tool: shows the finger trail while dragging (no silent drop of drags longer than 600 ms; long paths are sampled to ≤ 12 points); applies the selection restricted to the connected regions the finger touched; in Remove mode, a selection that would remove ≥ 60 % of the garment's visible area is not applied and a one-line hint says "That selects the whole garment. Tap the background or hanger pieces, or use the brush." (ES/DE provided by worker); the selector always sees the cutout over a neutral grey (PR #134). Developer mode overlays the raw selection mask for 1 s after each tap and writes a tap dump (input, mask, point) to `cutout-debug/editor/`. Any wiring defect found by G-CUT-DIAG is fixed here. Note for Manu: the smart tool selects whole objects (magic_touch semantics, verified in Python): a tap on the garment selects the whole garment; it is meant for leftover background pieces and hanger parts.
- **REQ-ED-02 Naming.** "Redo cutout" becomes "Cut out again" (ES "Volver a recortar", DE "Erneut freistellen") so it no longer clashes with Redo.
- **REQ-ED-03 Full history (answer 8).** The editor keeps the complete history of the session: every smart/brush/reset step and every "Cut out again" run can be undone and redone (Undo ↶ and Redo ↷ buttons; a new edit after an undo drops the redo tail). Memory: masks stored as bit runs/stroke lists, "Cut out again" photos kept as temp files in the cache dir; total in-memory history ≤ 64 MB; temp files deleted when the editor closes. History ends when the editor closes (Done or Cancel); it is not kept with the garment.
- **REQ-ED-04 (#135 D1)** = REQ-OR-05 (Keep mode restores from the original) and "Cut out again" becomes available for saved garments that have an original.

## Batch add (N1, N2)
- **REQ-BA3-01 Cancel and exit (N1).** The batch screen has a close (✕) button in the top bar at every stage. Tapping it, or Back, shows the existing discard dialog when drafts exist ("Discard this batch? Processing stops and unsaved garments are lost." — Keep editing / Discard). Discard cancels the processing job first, then deletes the temp files (raw copies, intermediates, cutouts) of every unsaved draft, then returns to Browse. A cancelled cutout never writes after the delete.
- **REQ-BA3-02 ETA (N2).** Premise check: an ETA exists (`ui/BatchEta.kt`) but appears only after two completions, resets whenever the user opens a draft or Settings, scrolls away with the list and starts too low with 2 parallel cutouts. New behaviour: the estimator lives with the batch state (not the screen), completions are stamped when they are published, the batch start counts as the first stamp, so an ETA shows from the first finished photo; the progress header (bar, "N of M", ETA) is pinned above the list; ETA text changes at most every 5 s and never jumps up by more than 20 % at once.
- **REQ-BA3-03** = REQ-PD-02 (a): one shared 60 s module wait per batch.
