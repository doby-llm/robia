Garment review — redesign proposals

Brief: Manu finds the garment review ugly (“el before and after, al ser palabras, tienen diferente longitud y al estar alineados a la izquierda en un chip que ocupa todo el espacio…”) and the Edit effect after a scan too loud for an optional button. Scope: tag review (category/occasion added, renamed or deleted), colour review (palette added/edited/deleted/restored), batch progress and completion. Design only — no Kotlin.

Recommendation: Finalist 1 — Checklist.

The review is a confirmation task: Robia already did the work and most suggestions are right. The Checklist turns 120 garments into one decision (“Apply 118 changes”) and makes disagreeing cheap (untick, or tap the row to pick). It removes the boxes that caused the asymmetry instead of balancing them, shows the change as text with the new value first, and leaves a single filled button on screen. It has the best error recovery: nothing is saved until Apply, and “Edit changes” on the calm completion screen reopens the list.

Keep Finalist 2’s ideas as parts of it: the row tap opens a sheet with the suggestion large (B’s hero), and the swatch-with-name + diff chips language is shared. Finalist 3 is the fallback if we want the smallest code change this round.

Dark theme note. Robia ships light only today (no dark scheme in Theme.kt; dark was out of scope, see artifacts/inv-r3-c.md). The dark phones use a derived proposal of the same Earth & Steel palette, defined in build.py (DARK). Accent: the repo tokens are espresso/champagne, not indigo; python3 build.py --accent indigo re-renders everything with an indigo accent if the pending palette change lands that way.

1 · What the user does today

After a tag or palette change is saved, a prompt offers a review. Robia scans garments (progress header), then lists one card per garment with a proposal: tag review — current tags of that kind → proposed tags (tap to pick, multi-choice for occasions); colour review — current main/secondary colour → proposed (tap a dot to pick). Each card: Accept / Discard; a manual-choice card has no proposal. Bottom: Accept all (N) / Save N accepted / Done. Back → “Discard changes?” (undoes the tag/palette change too). Commit → completion screen (check + sparkles, 1.6 s auto-dismiss). Data per item: photo, (no name), before value(s), after value(s), proposal kind (suggested vs choose manually). No confidence value is shown or stored per proposal.

  1. Ragged boxes (Manu’s hypothesis — confirmed). Tag review stacks two full-width pills, text left-aligned: “Party, Casual” and “Party, Casual, Work ▾” end at different x, while the ↓ between them is centred. Three different alignment axes in one card.
  2. The tap target hides in the text. The “To” pill is also the picker; the only affordance is a “▾” glued to the end of the label, so it moves with the text length.
  3. No diff. “From” and “To” repeat the whole set; the user has to compare lists to find the one tag that changed (Work).
  4. Buttons outweigh the content. Every card has a filled Accept + outlined Discard at half width (48 dp), plus a filled “Accept all” at the bottom: 2N+1 heavy buttons, three of them filled on one screen. “Discard” is ambiguous (discard the garment? the suggestion?).
  5. The header shouts after it’s done. “Garment scan · 120 / 120 garments” in bold titleLarge with an 8 dp bar stays as the biggest thing on screen after the scan ends.
  6. Slow for big batches. 112 dp photo column + 24 dp gaps → ~2.5 cards per screen; 120 garments ≈ 50 screens of scrolling and 2 taps each.
  7. No garment name, no undo. Cards don’t say which garment it is; an accepted card slides away after 200 ms and can’t be brought back.
  8. Colour review shows dots only. Four 28 dp dots (below the 48 dp target) with no names: “Navy” vs “Black” or “Beige” vs “Cream” are indistinguishable, and the dots are also the picker buttons.
  9. Completion and Edit effects are louder than the decision. Sparkle burst + scale-in on completion; the optional “Edit photo” after a scan gets its own SparkleBurst and a terracotta ✦ — the loudest thing on the screen is an optional action.

D · Checklist with opt-out

Ticked list + one Apply bar. New value first in text, “was …” under it; tags as diff chips.

Fastest for 100+ (0 taps if all good), one primary, list layout immune to length differences. Risk: users may Apply without looking — mitigated by readable rows and the Edit changes exit.
