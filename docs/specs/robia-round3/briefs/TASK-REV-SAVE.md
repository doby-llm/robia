# TASK-REV-SAVE — Save each garment as it leaves the list; leave halfway

## Goal
F21 (REQ-FB-21, R3-DEC-050, R3-DEC-053, R3-DEC-054 items 4–6): today nothing is saved until the end (`onCommit(List<ClothingItem>)`), and leaving discards the proposals. The design says each garment is saved as it leaves the list and leaving halfway keeps every garment already decided. This is the task that writes user data: it replaces the commit at the end with one live, guarded, serial write per decided garment. It is the task the independent reviewer reads line by line.

## Steps
1. **Screen state.** The screen holds a `TagReviewSession` (cards are added as the scan finds them, each with `reviewChangesFor`); the id lists `acceptedIds`/`discardedIds`/`hiddenIds`, `commitUpdatedItems`, `tagReviewCommitCandidates`, `tagReviewOpenAcceptableCount` and `shouldAutoCommit` are deleted. The exit animation keys on "decision is not Pending" and a local hidden set as before.
2. **Deciding.** Apply, Keep as is and Got it call `session.apply(id)`: no delta → nothing is written; a delta → `onApply(listOf(delta))`, a `suspend (List<TagDelta>) -> Result<List<AppliedDelta>>` parameter. The card leaves the list at once; when the result arrives the screen calls `appliedResult` (one per garment), on failure `applyFailed` (the card returns to the list) and a snackbar `review_apply_failed`. Reject calls `session.reject(id)`: nothing is written. A tap on a decided card does nothing.
3. **The write (RobiaApp).** One function used by `onApply` and by the `onRevert` parameter (same type shape with `AppliedDelta`, wired now, first used by REV-UNDO): it runs in the same serial chain as the other review writes (wait for `ReviewWrites.latest` the way `launchUndo` does), then in that one coroutine: plain-read the live garments by id and the live tag table (`currentGarmentsForUndo`-style; never `readGarmentsForReview`, which joins the latest write and would join itself), call `applyDelta` / `revertDelta` per garment with `categoryId = changeSet.categoryId` and the live tags, `wardrobeRepository.upsertItems(changedItems)`, and enqueue one `WardrobeSyncOperation.UpsertItem` per written garment detached, as `ReviewWrites.launch` does; return the `AppliedDelta` of every garment (empty when nothing changed or the garment is archived or gone). A thrown error becomes a failed `Result`, never a crash and never a half-written batch (one `upsertItems` call per batch).
4. **Finishing.** When `session.isComplete(scanning)` the screen calls `onFinish(changedGarments)`; RobiaApp keeps today's behaviour for now: the completion overlay with `reviewCompleteText(ReviewCompleteKind.Tags, n)` and `replaceRoute(RobiaRoute.ManageTags)` (REV-DONE replaces the overlay). `commitTagReview(List<ClothingItem>)` is deleted.
5. **Leaving.** The screen reports `session.appliedGarmentCount()` to RobiaApp whenever it changes (a callback; RobiaApp keeps it in state, zero when no review is open) and both back entries (the screen's `BackHandler` and the shell handler at ~1675) go through `requestTagReviewDiscard()`. `leaveKind(count)`: `Discard` shows today's dialog unchanged (confirm = `discardTagReview`, which undoes the whole tag change); `Leave` shows a new dialog: title `review_leave_title`, body plural `review_leave_body`, confirm `review_leave` (leaves: clears the active review and the dialog and goes to Manage tags, no undo, applied garments and the tag change stay), dismiss `review_keep_reviewing`. Pending writes finish after the screen is gone (they run on the app scope). Nothing resumes after process death.

The rest stay as they are." | "1 prenda ya está actualizada. El resto se queda como está." | "1 Kleidungsstück ist schon aktualisiert. Der Rest bleibt unverändert.", other "%1$d garments are already updated. The rest stay as they are." | "%1$d prendas ya están actualizadas. The garment is back in the list." | "No se pudo guardar. La prenda vuelve a la lista." | "Speichern fehlgeschlagen. Das Kleidungsstück ist wieder in der Liste."
7. **Tests** (`TagReviewSaveTest`, fakes for the live read and the repository, `runBlocking` as `ReviewUndoOrderTest` does): the V-REV-SAVE-1 to -3 rows. The serial write is a small testable function (inputs: previous job, live reads, repository fake) so the chain order, the live-read rule and the one-batch-one-`upsertItems` rule are JVM tests, not text greps.
