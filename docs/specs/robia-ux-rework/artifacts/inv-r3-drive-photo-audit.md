# Robia Google Drive photo durability audit

Scope: read-only source audit of `src/` (commit `fc45cec`). No production code was changed; no Gradle/Android build was run.

## Scenario findings

### Replacement, deletion, and concurrent edits

The replacement ordering is sound: changed WebP is uploaded, the JSON snapshot is committed, and only then are unreferenced paths purged. A process death before the snapshot leaves an orphan rather than deleting the old referenced blob; the next successful cycle can sweep it (`sync/GoogleDriveWardrobeRepository.kt:405-420`, `463-492`). Existing tests cover changed-photo replacement and failure safety (`app/src/test/java/com/gusanitolabs/robia/sync/UploadChangeDetectionTest.kt:33-64`).

Archive is represented by a local tombstone and the sync export excludes archived garments (`data/LocalRepositories.kt:79-95`; `sync/LocalWardrobeSyncSnapshotRepository.kt:58-69`). That is safe against a remote device resurrecting a deliberately deleted item, but deletion is a destructive user decision: once the tombstone-bearing snapshot succeeds, the associated blobs are eligible for purge. There is no photo undelete path in the gateway (`sync/WardrobeSyncGateway.kt:17-25`).

The merge machinery preserves a guarded photo over a phone file and does not silently replace the phone reference when remote hydration fails (`sync/LocalWardrobeSyncSnapshotRepository.kt:142-153`, `602-609`; `app/src/test/java/com/gusanitolabs/robia/sync/GuardedPhotoRestoreTest.kt:30-60`). The gap is that a remote record can be copied without verifying its blob is present in the current Drive index. A prior deletion, malformed snapshot, or external mutation can therefore remain a metadata pointer to nowhere (`sync/GoogleDriveWardrobeRepository.kt:388-400`).

### Restore and local durability

Restore has strong failure containment: missing path, 404, timeout, decode failure, and local-write failure become a guarded record rather than a placeholder photo (`sync/GoogleDriveWardrobeRepository.kt:1108-1124`, `1137-1215`). Import writes a photo URI only after successful materialization; guarded rows become `NeedsUserAction` with a bounded retry deadline and user-visible message (`sync/LocalWardrobeSyncSnapshotRepository.kt:509-550`, `628-638`). Automatic retry runs each sync (`sync/WardrobeSyncOutboxProcessor.kt:364-367`). This answers “can the app tell the user?”: yes, through the guarded/attention state; “Keep without photo” is explicit and does not delete the remote blob (`sync/WardrobeSyncOutboxProcessor.kt:400-411`, `sync/WardrobeSyncGateway.kt:24-25`).

However, integrity is incomplete. Restore records fetched byte count and SHA-256, and checks image bounds, but accepts any decodable bytes rather than requiring `actualSize == photo.byteSize` and `actualHash == photo.contentHash` (`sync/GoogleDriveWardrobeRepository.kt:1159-1204`). A valid but wrong/truncated image can become the local authoritative file. The same missing verification exists on upload: `upsertBlob` returning success is enough to write the hash/size into the snapshot (`sync/GoogleDriveWardrobeRepository.kt:436-451`, `700-723`).

The app persists only one canonical photo URI. Background-removal/quick-edit flows update `currentEditedUri`, and quick edit creates a processed output (`ui/AddEditClothingScreen.kt:677-705`), but the sync mapper serializes only `ClothingItemEntity.photoUri` (`sync/LocalWardrobeSyncSnapshotRepository.kt:443-463`). Drive additionally canonicalizes the selected image to lossy WebP (`media/ClothingImageStore.kt:58-92`). Thus the edited display photo can be restored, but the raw source and exact original bytes are not Drive backup artifacts. If re-editing from the raw source or lossless recovery is a product requirement, this is a major data-loss gap, not merely an implementation detail.

## Proposed tasks (minimal fixes and JVM tests)

1. **Add a fail-closed photo integrity contract.** In `GoogleDriveWardrobeRepository.kt`, after upload verify Drive metadata/read-back size and hash; during restore compare fetched bytes to `GarmentPhotoRecord.byteSize/contentHash` and guard on mismatch. Add JVM tests to `RestoredPhotoReuploadTest.kt` or a new `PhotoIntegrityTest.kt` for zero-byte, truncated, wrong-valid-image, and hash/size mismatch cases. Touch: `GoogleDriveWardrobeRepository.kt`, `DriveSnapshotApi` fake, tests.
2. **Validate `CopyRemote` and merged records.** Require the exact blob path (or an unambiguous legacy candidate) to exist before carrying a remote record forward; otherwise mark it guarded and keep any phone-held file. Add a JVM test with a remote photo record absent from `DriveFileIndex` and assert no successful snapshot claims it is restorable. Touch: `GoogleDriveWardrobeRepository.kt`, `MergeDecision`/snapshot-merge code if needed, `GuardedPhotoRestoreTest.kt`.
3. **Define raw-vs-edited durability explicitly.** If raw recovery is required, add separate raw and canonical/edited blob records to `SyncModels.kt`, serialize/import both in `GoogleDriveWardrobeRepository.kt` and `LocalWardrobeSyncSnapshotRepository.kt`, and retain them through editor save paths. Add round-trip JSON and restore tests. If it is not required, remove the implied raw retention or show a clear “Drive stores the edited image only” warning. Touch: `SyncModels.kt`, `PhotoBlobKeys.kt`, `GoogleDriveWardrobeRepository.kt`, `LocalWardrobeSyncSnapshotRepository.kt`, editor tests.
4. **Enforce account binding.** Persist the authorized account identity, compare it before every read/write, and require an explicit user choice on mismatch; never treat a new account’s empty appDataFolder as a clean backup. Add a JVM state/processor test for account A → account B and a device test using two Google accounts. Touch: settings/state repository, `WardrobeSyncGateway.kt`, `GoogleDriveWardrobeRepository.kt`, processor tests.
5. **Replace truncated keys and add a read-only integrity checker.** Use full SHA-256 (or a versioned full digest) for new blob names, with migration tests for old 16-hex keys. Add `PhotoIntegrityCheck` that reads Room photo references/local files, lists Drive `appDataFolder` metadata, and downloads referenced blobs read-only when a hash is needed. Report: missing local file, missing Drive path, size mismatch, hash mismatch, zero-byte/corrupt decode, orphan, and ambiguous duplicate. Existing pieces are `ClothingImageStore.readImageBlob` (local hash), `DriveSnapshotApi.listAll`/`fetchBlobToFile` (Drive inventory/download), and `GarmentPhotoRecord` hash/size fields (`media/ClothingImageStore.kt:48-55`; `sync/GoogleDriveWardrobeRepository.kt:538-540`, `683-698`; `core/model/SyncModels.kt:187-205`). Add pure JVM comparison tests; run the actual content-URI/Room/Drive check on a device.
6. **Add safe local-file reconciliation.** Enumerate app-private image/thumbnail files, delete only unreferenced thumbnails and orphaned temp files, and write capture/processed output through temp-plus-atomic-rename. Add a JVM planner test proving referenced and guarded files are never selected for deletion. Touch: `ClothingImageStore.kt`, new integrity/reconciliation helper, tests.

## Device checks

- Fresh install → add photo → kill process at each stage (copy, edit, upload, snapshot) → relaunch and verify local image plus Drive record/blob.
- Edit/replacement during airplane mode, then restore connectivity; verify old blob remains until the snapshot succeeds.
- Restore with missing blob, zero-byte blob, truncated blob, valid wrong-image bytes, and only one of local/Drive photo present; verify guarded UI, retry, and no overwrite of a phone-held file.
- Two-device concurrent edit/delete/restore, including a guarded remote record and an archived garment.
- Fill device storage and Drive quota; revoke authorization, switch accounts, sign out/in, clear app data, and uninstall before first sync. Verify explicit blocked/attention states and that no account’s empty appDataFolder is mistaken for the user’s backup.
- Run the read-only integrity checker against a populated appDataFolder and confirm every reported mismatch is actionable without deleting anything.

**Resumen para Manu:**
La secuencia subir foto → guardar snapshot → borrar blobs viejos protege bien contra pérdidas accidentales.
El riesgo principal es que no se compara hash/tamaño real después de subir o descargar una foto.
El backup de Drive guarda una sola foto editada; la fuente original no queda recuperable.
