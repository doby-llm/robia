# TASK-B01 — Pipelined batch processing

## Goal
Adding many garments at once is slow because the batch runs strictly one garment at a time (`BatchProcessingCoordinator.processQueued`: `while (true) { firstOrNull { Queued } → processDraft }`). Each garment = cutout (ML Kit, ~1–2 s) → crop/palette → suggestion (EmbeddingGemma image embedding, ~1.6 s median on Poco F3, behind the engine's single `Mutex`). Manu wants several garments in flight while the screen still shows them finishing in order (REQ-BA-01, PROC-DEC-004). Overlap the stages: cutouts of the next garments run while the single suggestion worker handles the previous one. Expected ≈ 40–45 % less wall time; measured on device (V-Z2-21).

## Steps
1. Split `processBatchDraft` into two internal suspend functions with the same code, no behaviour change: `cutoutStage(draft, context, backgroundRemover, mainColors): CutoutStageResult` (everything up to and including palette: source aspect, background removal, crop, display aspect, colours, fallback flag) and `suggestStage(draft, cutout, suggestionService, availableTags, context): BatchDraftItem` (suggestion + final status/message, exactly as today). Keep `processBatchDraft` as `cutoutStage` + `suggestStage` for any other caller (grep). Exceptions: inside `cutoutStage` any non-cancellation exception is returned as `CutoutStageResult.Failed(message)`; inside `suggestStage` it yields a Failed draft (same message rule as today's catch); `CancellationException` is always rethrown.
2. Coordinator (algorithm = TS§B01 "ordered window"; all coordinator state is touched only on the scope's dispatcher, Main in the app): new signature `processQueued(drafts: () -> List<BatchDraftItem>, cutout: suspend (BatchDraftItem) -> CutoutStageResult, suggest: suspend (BatchDraftItem, CutoutStageResult) -> BatchDraftItem, publish: (BatchDraftItem) -> Unit, onInterrupted: (BatchDraftItem) -> Unit)`; parallelism read from `internal object BatchParallelism { @Volatile var cutouts: () -> Int = { 2 } }` (declare it in this file).
   - If the job is active: set `restartRequested = true` and return.
   - Otherwise launch ONE job: `val p = BatchParallelism.cutouts().coerceIn(1, 2)`; `val permits = Semaphore(p)`; `window = ArrayDeque<Pair<BatchDraftItem, Deferred<CutoutStageResult>>>()` with max size `p + 1`.
   - Loop: (a) top up — while `window.size < p + 1`, pick the Queued draft with the lowest `orderIndex` whose id is not in the window (re-read `drafts()`), `publish(it.copy(status = Processing, explicitlyAccepted = false, errorMessage = null))`, add `it to async { permits.withPermit { cutout(it) } }`; (b) if the window is empty: if `restartRequested` or any Queued draft exists → clear the flag and continue, else break (job ends); (c) head = `window.removeFirst()`; `val r = head.second.await()`; if `r` is Failed → `publish(head.first.copy(status = Failed, errorMessage = r.message))`, else `publish(suggest(head.first, r))`.
   - Final states are therefore published in dispatch order (screen order), one suggestion at a time, with at most `p + 1` results alive.
3. Cancellation: keep `cancel()` and `terminalizeActiveDrafts` exactly as today (owned drafts Queued/Processing → `onInterrupted`); cancelling the job cancels the window's `async` children; unpublished results are dropped. Keep the "late old coroutine must not terminalize a replacement batch" guard (`processingJob === coroutineContext[Job]` in `finally`).
4. `RobiaApp.processQueuedBatchDrafts` (only this block): pass `cutout = { cutoutStage(it, context, batchBackgroundRemover, mainColors) }`, `suggest = { d, r -> suggestStage(d, r, suggestionService, availableTags, context) }`, `publish = ::updateBatchDraft` and the existing `onInterrupted`. `BatchParallelism.cutouts` stays at its default 2 here; SG2a sets it for the precise engine.
5. Logging (developer): Logcat tag `RobiaBatch`, one line per garment `batch_item idx=%d cutout_ms=%d suggest_ms=%d wait_ms=%d` and at the end `batch_total_ms=%d items=%d` (no URIs, no personal data).
6. Contract test: rewrite `batchCoordinator_processesAll60QueuedItemsSeriallyToTerminalStates` (tasks.md rule 11) to pin the new design: `processingJob?.isActive == true`, `Semaphore(`, ordered publication (the name you gave the suggestion loop), and keep its other assertions (app wiring, terminal states) adapted to the new names. Keep `batchCancellation_terminalizesTheCurrentItemForManualRetry` green unchanged if possible.

## Tests
`BatchProcessingCoordinatorTest` — keep the 3 existing tests (adapt only the call signature) and add, with `CompletableDeferred` gates and counters in the fakes: (a) 60 drafts all terminal and the job completes; (b) parallelism 2 → never more than 2 cutouts and 1 suggestion in flight, never more than 3 results alive; (c) draft 2's cutout finishing before draft 1's → draft 2's final state is published after draft 1's; (d) cutout failure on draft 3 and suggestion exception on draft 5 → both Failed, others finish; (e) cancel mid-run → no draft left Queued/Processing; (f) parallelism 1 → at most one cutout at a time; (g) Retry of an earlier Failed draft while the job runs → it is processed; (h) `processQueued` called after the last publish but before the job ends → the newly Queued draft is processed (nothing left Queued).
