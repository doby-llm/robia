## §B Batch add (rev 2)
### B01 — Pipelined batch processing — `ui/BatchProcessingCoordinator.kt`, `ui/BatchAddClothingScreen.kt` (`processBatchDraft` split only), `ui/RobiaApp.kt` (`processQueuedBatchDrafts` block ~1195-1216 only), `app/src/test/java/com/gusanitolabs/robia/RegressionSourceContractTest.kt` (`batchCoordinator_processesAll60QueuedItemsSeriallyToTerminalStates` only), `app/src/test/java/com/gusanitolabs/robia/ui/BatchProcessingCoordinatorTest.kt`
- Today: `processQueued` runs `while (true) { firstOrNull { Queued } → processDraft }` strictly serially; each draft = cutout (ML Kit, ~1-2 s) → crop → palette → `suggestForPhoto` (EmbeddingGemma image embedding ~1.6 s median on Poco F3, behind the engine's single `Mutex`).
- New: `processDraft` is split into `cutoutStage(draft): CutoutStageResult` (status Processing, background removal, crop, aspect, palette — no suggestion; any non-cancellation exception is caught and returned as `CutoutStageResult.Failed(message)`) and `suggestStage(draft, cutout): BatchDraftItem` (suggestion + final status; a non-cancellation exception gives a Failed draft with the same message rule as today's `processBatchDraft` catch).
- Coordinator algorithm (all coordinator state is touched only on the scope's dispatcher, Main in the app): one job runs an **ordered window** loop:
  1. `window` = list of (draft, `Deferred<CutoutStageResult>`) in dispatch order, max size `W = cutoutParallelism + 1`.
  2. Top up: while `window.size < W`, take the Queued draft with the lowest `orderIndex` that is not already in the window (re-reading `drafts()` each time), publish it as Processing, and start its cutout as an `async` child that first acquires a `Semaphore(cutoutParallelism)` permit.
  3. If the window is empty: if `restartRequested` is set or `drafts()` still has Queued drafts, clear the flag and continue; otherwise exit the loop (the job completes).
  4. Head: `await` the first window entry's cutout; Failed → publish a Failed draft; otherwise run `suggestStage` (one at a time, so the embedding Mutex is never contended) and publish the result; remove the head; go to 2.
  - Publication order = dispatch order, so final states appear in screen order; a Retried draft is simply dispatched again when it is the lowest Queued draft.
  - `processQueued` called while the job is active sets `restartRequested = true` instead of returning silently (fixes a Retry arriving while the job winds down).
  - Bounded memory: at most W cutout results/decoded photos alive.
- `cutoutParallelism` comes from `internal object BatchParallelism { @Volatile var cutouts: () -> Int = { 2 } }` (B01). SG2a sets `BatchParallelism.cutouts = { if (CutoutEngineRegistry.isPreciseActive()) 1 else 2 }` in `RobiaApplication` (cheap boolean, no engine construction).
- Cancellation: `cancel()` cancels the job (and its cutout children); every owned draft still Queued or Processing becomes Interrupted via the existing `terminalizeActiveDrafts`; window results not yet published are dropped (their drafts were Processing → Interrupted, Retry available). The "late old coroutine must not terminalize a replacement batch" rule is kept.
- Memory/timing on device: V-Z2-21 (batch of 10 with the precise pack ON and OFF: no crash, developer `RobiaBatch` lines, total time compared with today).
- Contract test: `batchCoordinator_processesAll60QueuedItemsSeriallyToTerminalStates` pins the serial loop (`while (true)`, `firstOrNull { it.status == BatchDraftStatus.Queued }`). B01 replaces that design, so the test is rewritten to pin the new one (rule 11): `processingJob?.isActive == true`, `restartRequested`, `Semaphore(`, `BatchParallelism`, and that all 60 queued items reach terminal states (the JVM test below proves it).
- JVM tests (`BatchProcessingCoordinatorTest`, fakes with `CompletableDeferred`): (a) 60 drafts all terminal and the job completes (`processingJob` cleared); (b) never more than 2 cutouts and 1 suggestion in flight, never more than 3 results alive; (c) draft 2 finishing its cutout before draft 1 is NOT published before draft 1; (d) cutout failure on draft 3 and suggestion exception on draft 5 → both Failed, the others finish; (e) cancel mid-run → no draft left Queued/Processing; the existing three cancellation tests still pass; (f) parallelism 1 → at most one cutout at a time; (g) Retry of an earlier Failed draft while the job runs → it is dispatched and finishes; (h) Retry (processQueued) called after the last publish but before the job completes → the draft is processed (no draft left Queued).
- Expected gain (planner estimate, to be measured in V-B01-3): with cutout ≈ 1.5 s and suggestion ≈ 1.6 s per garment, wall time per garment drops from ≈ 3.1 s to ≈ max(1.6, 1.5/2) ≈ 1.6-1.8 s (≈ 40-45 % faster). Embedding remains the bottleneck: running two embeddings at once is out of scope (one native engine, memory).
